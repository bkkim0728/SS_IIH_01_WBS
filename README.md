# 프로젝트 일정관리 (WBS HUB)

삼성증권 **SS-SIIIDS 투자정보 HUB + 해외시세 감시** 프로젝트의 WBS 진척 관리 도구입니다.
`template_SS-SIIIDS_WBS_v0_4.xlsx` 를 그대로 옮겨 담았습니다.

| 항목 | 값 |
|---|---|
| Task | 151건 (L1 5 · L2 5 · L3 31 · **L4 리프 110**) |
| 마일스톤 | 8개 |
| 기간 | 2026.09.01 → 2027.07.02 (**44주**) |
| 산출물 | 34종 |
| 단계 가중치 | 분석/설계 25% · 개발 40% · 테스트 20% · 이행 5% · 안정화 5% |

**스택**: 정적 HTML/CSS/JS (빌드 없음) · Supabase(Postgres) · Render(정적 호스팅) · GitHub

## 3. Supabase 연결하기

팀이 같은 진척을 보려면 이 단계가 필요합니다.

1. [supabase.com](https://supabase.com) 에서 새 프로젝트를 만듭니다. 리전은 **Northeast Asia (Seoul)** 을 고르세요.
2. 좌측 **SQL Editor > New query** 로 이동합니다.
3. `supabase/schema.sql` 전체를 붙여넣고 **Run**.
4. 새 쿼리를 열어 `supabase/seed.sql` 전체를 붙여넣고 **Run**.
5. 확인:
   ```sql
   select level, count(*) from tasks group by level order by level;
   -- 1|5  2|5  3|31  4|110
   select * from v_task_rollup;
   ```
6. **Project URL 과 API 키를 복사합니다.** 아래 "키를 못 찾을 때" 참고.
7. 앱의 **설정** 화면에 붙여넣고 **연결하고 새로고침**을 누릅니다.

### 키를 못 찾을 때

Supabase 가 대시보드를 개편해서, 예전에 `Settings > API` 한 화면에 같이 있던 것이
**`Settings > Data API`(URL)** 와 **`Settings > API Keys`(키)** 로 갈라졌습니다.
옛 튜토리얼을 따라가면 안 나옵니다.

**가장 빠른 길: 프로젝트 상단의 `Connect` 버튼.** URL 과 키가 한 화면에 같이 나옵니다.

직접 찾으려면:

| 필요한 값 | 위치 |
|---|---|
| Project URL | `Settings > Data API` → **Project URL** |
| API 키 | `Settings > API Keys` → **Publishable key** |
| (레거시) anon 키 | `Settings > API Keys` → **Legacy API Keys** 탭 |

URL 은 주소창에서도 알 수 있습니다. 대시보드 주소가
`https://supabase.com/dashboard/project/abcdefgh...` 라면
Project URL 은 `https://abcdefgh....supabase.co` 입니다.

**Publishable 키가 안 보이면** `Settings > API Keys` 에서 **Create new API keys** 를 누르세요.
기존 anon 키는 그대로 살아 있으니 안전합니다.

### 어느 키를 넣어야 하나

| 키 | 형식 | 이 앱에 |
|---|---|---|
| **Publishable** | `sb_publishable_...` | ✅ 권장 |
| anon (레거시) | `eyJhbGciOi...` | ✅ 됨 (2026년 말 지원 종료 예정) |
| Secret | `sb_secret_...` | ❌ 절대 금지 |
| service_role (레거시) | `eyJhbGciOi...` | ❌ 절대 금지 |

Secret 계열은 RLS 를 통째로 우회하므로 브라우저에 넣으면 DB 전체가 열립니다.

> 앱은 두 형식을 자동으로 구분합니다. 새 publishable 키는 JWT 가 아니라서
> `Authorization: Bearer` 헤더에 넣으면 Supabase 가 거부하기 때문에, JWT 로 시작하는
> 레거시 키일 때만 그 헤더를 붙입니다.

### 권한 정책 고르기

`schema.sql` 안에 두 가지가 들어 있습니다. 기본은 A안입니다.

| | 누가 볼 수 있나 | 누가 고칠 수 있나 | 언제 쓰나 |
|---|---|---|---|
| **A안** (기본) | 링크를 아는 사람 | 링크를 아는 사람 | 사내 공유, 빠른 시작 |
| **B안** | 링크를 아는 사람 | 로그인한 사람만 | 고객사 공유, 감사 대응 |

B안으로 바꾸려면 `schema.sql` 6번 섹션에서 A안 `write all` 정책을 지우고
B안 주석을 해제한 뒤, Supabase **Authentication** 에서 사용자를 초대하세요.

## 4. Render에 배포하기

1. [render.com](https://render.com) 로그인 → **New > Blueprint**
2. 방금 올린 GitHub 저장소를 선택합니다. `render.yaml` 을 자동으로 읽습니다.
3. **Environment** 에 두 값을 넣습니다.

   | Key | Value |
   |---|---|
   | `SUPABASE_URL` | `https://xxxxxxxx.supabase.co` |
   | `SUPABASE_ANON_KEY` | `sb_publishable_...` 또는 `eyJhbGciOi...` |

4. **Apply** 를 누르면 `build.sh` 가 이 값들을 `assets/js/config.js` 로 구워 넣습니다.
   접속하는 모두가 별도 설정 없이 Supabase 모드로 들어옵니다.

정적 사이트라 슬립이 없고, main 브랜치에 push하면 자동 재배포됩니다.

### 진척을 바꾸면 저장이 실패할 때

**읽기는 되는데 쓰기만 안 되는 경우입니다.** 스키마 결함이었습니다.

`tasks` 를 UPDATE 하면 트리거가 `task_log` 에 INSERT 를 합니다. 그런데 `task_log` 는
RLS 가 켜져 있고 INSERT 정책이 없었으며, 트리거 함수도 `security definer` 가 아니라
호출자(anon) 권한으로 돌았습니다. 로그 INSERT 가 막히면 트랜잭션이 통째로 되돌려지면서
UPDATE 까지 함께 실패합니다.

**고치는 법** — Supabase SQL Editor 에서 `supabase/fix-write-permission.sql` 을 실행하세요.
데이터를 건드리지 않고, 여러 번 실행해도 안전합니다. 마지막에 쓰기 테스트까지 해 줍니다.

새로 설치하시는 경우 `schema.sql` 은 이미 고쳐져 있어 이 작업이 필요 없습니다.

**원인을 직접 확인하려면** 설정 화면의 **쓰기 테스트** 버튼을 누르세요.
한 건을 썼다가 곧바로 되돌리고, Supabase 응답 원문을 그대로 보여줍니다.

| 나오는 응답 | 뜻 |
|---|---|
| `쓰기 성공` | 정상입니다 |
| `42501 ... task_log` | 이 문서의 결함. `fix-write-permission.sql` 실행 |
| `응답이 빈 배열입니다` | tasks 에 UPDATE 정책이 없음. 같은 파일 실행 |
| `42501 permission denied for table tasks` | 테이블 GRANT 누락. 같은 파일 실행 |
| `401 Invalid API key` | 키가 실제로 틀림. Publishable 또는 anon 키인지 확인 |

### 배포 후 문제가 생길 때

앱의 **설정** 화면 오른쪽 **진단** 카드를 먼저 보세요. 글꼴이 내려왔는지, 지금 보고 있는
CSS 가 몇 번째 배포인지, Supabase 가 어떤 URL 로 붙고 있는지가 한 줄씩 나옵니다.

**`PGRST125 Invalid path specified in request URL`**

Project URL 모양이 깨진 경우입니다. 아래 둘 중 하나입니다.

| 잘못 넣은 값 | 만들어지는 경로 |
|---|---|
| `https://xxx.supabase.co/` (끝 슬래시) | `//rest/v1/...` |
| `https://xxx.supabase.co/rest/v1` | `/rest/v1/rest/v1/...` |

앱이 이제 두 경우를 모두 자동으로 잘라내지만, Render 환경변수는
`https://xxx.supabase.co` 형태로 넣는 것이 정확합니다.

진단 카드의 **코드 버전(store.js)** 이 "실패" 로 나오면, `app.js` 는 새것인데
`store.js` 가 옛 캐시인 상태입니다. 강력 새로고침 한 번이면 풀립니다.

**스타일이나 글꼴이 바뀌지 않을 때**

브라우저가 옛 `app.css` 를 붙들고 있는 경우입니다. `render.yaml` 이 이제
CSS/JS/HTML 에 `no-cache` 를 주고, `build.sh` 가 배포마다 `?v=커밋해시` 를 붙입니다.

버전 스탬프는 세 곳 모두에 붙습니다. **셋 중 하나라도 빠지면 옛 파일이 섞여 돕니다.**

1. `index.html` → `app.css`, `app.js`, `config.js`
2. `app.js` 안의 `import './store.js'`
3. `store.js` 안의 `import './seed.js'`

이미 캐시된 브라우저는 한 번만 강력 새로고침 하세요.

- Windows: `Ctrl` + `Shift` + `R`
- Mac: `Cmd` + `Shift` + `R`

진단 카드에서 **글꼴 파일 경로**가 실패로 나오면 캐시가 아니라 파일이 안 올라간 것입니다.
`git status` 로 `assets/fonts/*.woff2` 4개가 커밋됐는지 확인하세요.

### Blueprint 오류가 날 때

**`services[0].plan no such plan free for service type web`**

정적 사이트(`runtime: static`)에는 `plan` 필드를 쓰지 않습니다. 요금제 개념이 없어 항상 무료이고,
`plan` 이 있으면 Render 가 웹 서비스 요금제 목록에서 값을 찾다가 실패합니다.
`render.yaml` 에서 `plan:` 줄을 지우세요.

**`./build.sh: permission denied`**

git 에 실행 권한(+x)이 실리지 않은 경우입니다. `buildCommand` 를 `bash build.sh` 로 두면 해결됩니다.
현재 `render.yaml` 은 이미 그렇게 되어 있습니다.

> **이 키를 공개해도 되나요?**
> 됩니다. publishable / anon 키는 브라우저에 노출되도록 설계된 값이고, 실제 접근 통제는 RLS 정책이 합니다.
> 다만 A안 정책은 링크를 아는 사람이 수정할 수 있다는 뜻이므로, 외부 공유 전에는 B안으로 바꾸세요.

### 계획일 자동 배치 (106건)

원본 M/N 열에 계획일이 들어 있는 Task는 **110건 중 4건**뿐입니다
(`2.1.1.3`, `2.1.5.2`, `2.1.6.1`, `2.1.9.2`).

나머지는 각 단계의 마일스톤 구간 안에서 영업일 기준으로 순서대로 배치했습니다.
원본 날짜를 가진 것은 `2.1.1.3`, `2.1.5.2`, `2.1.6.1`, `2.1.9.2` 네 건뿐입니다.

트리 화면에서는 두 종류를 **같은 색으로** 보여 줍니다.
어느 쪽인지는 날짜 칸에 마우스를 올리면 툴팁으로 나오고,
엑셀의 숨은 구분값(`tasks.date_source`)에도 그대로 남아 있습니다.
DB의 `tasks.date_source` 컬럼(`file` / `auto` / `rollup`)으로도 구분됩니다.

실제 일정이 정해지면 그대로 덮어쓰면 됩니다. 자동값은 아무것도 잠그지 않습니다.

### 작업명 빈 칸 (5건)

`3.1.2.1`, `3.1.2.2`, `3.1.2.3`, `6.1.3.2`, `6.1.3.3` 은 원본에 작업명이 비어 있어
`(작업명 미정)` 으로 표시됩니다. 채워야 할 자리로 남겨 두었습니다.

### 가중치

전체 비중(O열)의 합이 **0.95** 입니다. 0.05가 비어 있고, 원본 15행에 `L1 = 0` 인 빈 행이
있는 것으로 보아 착수 단계 몫으로 보입니다. 임의로 채우지 않고 원본 그대로 두었으며,
전체 진척률은 존재하는 가중치 합(0.95)으로 정규화해 계산합니다.

### 앱에서 직접 고치기

WBS 트리에서 **작업명 · 계획시작 · 계획종료**를 눌러 바로 고칩니다.
엑셀을 거치지 않아도 되는 소소한 수정에 씁니다.

작업명은 **모든 단계**에서, 날짜는 **L1~L4 전부** 고칠 수 있습니다.
눌러서 고치고 엔터, `Esc` 로 취소합니다. 날짜는 달력에서 고르면 바로 저장됩니다.

#### L4 (말단 Task)

그 Task 의 날짜를 그대로 바꿉니다.

**계획시작을 종료보다 뒤로 옮기면 일정을 미루는 뜻으로 봅니다.**
간트에서 막대를 끄는 것처럼 **기간을 유지한 채** 종료도 함께 옮깁니다.
반대로 종료를 시작보다 앞으로 당기는 건 실수일 가능성이 높아 막습니다.

#### L1~L3 (상위 단계)

상위 날짜는 자식에서 계산되는 값이라, 그 자리에 값을 넣어봐야 바로 덮어써집니다.
그래서 **자식들을 실제로 움직입니다.** 점선 밑줄로 구분되고, 마우스를 올리면 주황색이 됩니다.

| 고치는 칸 | 하는 일 |
|---|---|
| **계획시작** | 그룹 전체를 그 차이만큼 이동. **내부 간격 그대로** |
| **계획종료** | 그룹의 끝을 정하는 Task 의 종료일만 그 날짜로 (늘리기·줄이기) |

```
2.1.1 계획시작을 9/1 → 9/15 로
  → "2.1.1 그룹 5건을 14일 뒤로 옮겼습니다."
     2.1.1.1  09.01~09.02  →  09.15~09.16
     2.1.1.3  10.01~12.01  →  10.15~12.15
```

단계(L1)를 옮기면 그 아래 41건이 한 번에 움직입니다. 몇 건이 움직였는지 알려 드립니다.
중간에 하나라도 실패하면 **전부 원래대로 되돌립니다.**

고친 내용은 상위 일정·일수·간트·달력·엑셀에 곧바로 반영됩니다.

### WBS 번호 정리

추가·삭제를 거치면 `2.1.2` 자리가 비는 등 번호에 구멍이 생깁니다.

**Task 를 지우거나 엑셀로 더하면 번호가 자동으로 정리됩니다.**
몇 건이 바뀌었는지 알려 줍니다.

```
6건을 지웠습니다. 번호 40건을 자동으로 정리했습니다.
반영 완료 — 수정 36 · 추가 5 · 삭제 0 · 번호 1건 자동 정리 · 날짜 208/208 일치
```

작업명·날짜·진척만 바뀐 경우에는 번호를 건드리지 않습니다.
직접 돌리고 싶을 때는 툴바의 **번호 정리** 를 쓰세요.

- **순서는 그대로 두고 번호만** 1부터 촘촘히 다시 붙입니다
- 작업명·날짜·진척·담당자는 건드리지 않습니다
- 누르면 `옛번호 → 새번호` 목록이 먼저 뜹니다. 확인 후 적용
- **L1 단계 번호(2,3,4,5,6)는 기본으로 그대로 둡니다.** 이미 공유된 번호라서입니다.
  체크박스를 켜면 1,2,3… 으로 함께 정리합니다

> **내려받아 두신 엑셀이 있으면** 번호가 달라져 맞지 않습니다. 정리한 뒤 다시 내려받으세요.
> 확인 창에도 같은 안내가 나옵니다.

Supabase 모드에서는 코드가 열쇠라 겹치지 않도록 임시 코드를 거쳐 두 번에 나눠 씁니다.
중간에 실패하면 화면이 원래대로 돌아갑니다.

### 마일스톤 (Main / Sub)

마일스톤 스파인 오른쪽의 **관리** 버튼에서 등록·수정·삭제합니다.

| 종류 | 표시 | 쓰임 |
|---|---|---|
| **Main** | 선 아래 큰 점 ◆ | 착수 · 개발 종료 · Grand Open 같은 큰 마디 |
| **Sub** | 선 위 주황 점 ◇ | 중간보고 · 산출물 검토 같은 작은 마디 |

- Main 은 순서대로 고르게 배치되고, **Sub 는 실제 날짜 위치**에 얹힙니다
- 목록은 날짜순으로 자동 정렬됩니다
- 이름 · 종류 · 시작(선택) · 기준일 · 메모를 적습니다
- 스케줄 달력의 날짜 칸과 "이 달의 마일스톤" 목록에도 함께 나옵니다

**저장 위치는 두 가지입니다.**

- `supabase/migrate-milestone-kind.sql` 을 실행했으면 → **팀 전체 공유**
- 실행 전이면 → 각자 브라우저에만 저장 (앱은 그대로 동작합니다)

기존 `milestones` 테이블에는 읽기·수정만 열려 있어 새 마일스톤을 만들 수 없었습니다.
이 SQL 이 `kind` 컬럼과 등록·삭제 권한을 함께 넣어 줍니다.

### 스케줄 달력

월별 달력에 Task 기간이 막대로 그려집니다.

- 여러 날에 걸친 Task 는 **주가 바뀌어도 이어지고**, 그 주를 벗어나는 쪽은 `◀` `▶` 로 표시됩니다
- 겹치는 Task 는 위아래 줄로 나뉘고, 자리가 모자라면 `외 N건` 안내가 나옵니다
- 막대 색은 상태입니다. 미착수 / 진행중 / 완료 / **지연**
- **마일스톤**은 날짜 칸에 `◆` 로, 공휴일은 빨강(임시공휴일은 보라)으로 표시됩니다
- 막대를 누르면 **WBS 트리에서 그 Task 를 찾아 줍니다**

위쪽에서 **단계 · 상태 · 레벨**로 걸러 볼 수 있습니다. 레벨은 고른 단계 하나만 보여줍니다.
L1 을 고르면 5개 단계가 큰 막대로, L4 를 고르면 실제 작업이 낱개로 보입니다.

막대 배치 방식은 업로드해 주신 worklog 앱의 달력에서 가져왔습니다.
한 주를 배경 7칸 위에 CSS 그리드로 겹쳐 놓고, 막대의 `grid-column` 으로 기간을,
`grid-row` 로 몇 번째 줄인지를 정하는 방식입니다.

### 상위 단계 일정은 자동입니다

L1~L3 의 계획시작·계획종료·일수는 저장값이 아니라 **자식 Task 들의 범위**입니다.
엑셀 반영이나 삭제로 하위가 바뀌면 상위가 즉시 따라옵니다. 간트·달력도 같은 값을 씁니다.

그래서 **엑셀에서 상위 단계의 날짜 칸은 회색(고정)** 입니다. 고쳐서 올려도 반영되지 않습니다.
말없이 버리지 않고, 미리보기에 `자동계산` 칸으로 몇 건이 무시됐는지 알려 줍니다.

상위 단계의 기간을 바꾸려면 그 아래 **L4 Task 의 날짜**를 옮기세요.

간트의 상위 막대는 하위 상태도 물려받습니다.

- 하위에 **지연** 이 하나라도 있으면 막대가 빨갛게 바뀌고 `지연` 딱지가 붙습니다
- 종료일이 지난 미완료 Task 가 있으면 `초과` 딱지가 붙습니다

### 일수는 어떻게 정해지나

어디서도 입력받지 않습니다. **계획시작~계획종료 사이 영업일**(양 끝 포함, **주말과 공휴일 제외**)을
그때그때 계산합니다. 화면과 엑셀이 같은 목록을 씁니다.

- 화면: `assets/js/holidays.js` 를 참조해 표시할 때마다 계산

## 8. 글꼴

본문은 **페이퍼로지(Paperlogy)** 를 자체 호스팅합니다. 배포본 TTF 를 웹용 woff2 로
포맷만 바꿔 `assets/fonts/` 에 넣었고, 디자인과 자족 이름은 그대로입니다.
SIL Open Font License 1.1 이라 이대로 재배포해도 됩니다 (`assets/fonts/LICENSE.txt`).

| 웨이트 | 파일 | 쓰이는 곳 |
|---|---|---|
| 400 Regular | `Paperlogy-400.woff2` | 본문, 설명 |
| 500 Medium | `Paperlogy-500.woff2` | L3 작업명, 마일스톤 이름 |
| 600 SemiBold | `Paperlogy-600.woff2` | 카드 제목, L2 작업명 |
| 700 Bold | `Paperlogy-700.woff2` | 화면 제목, L1 단계명 |

원본 9종 중 4종만 씁니다. 한글 11,172자를 모두 담아 웨이트당 약 160KB,
합계 약 640KB 입니다. 400 과 600 은 `preload` 로 먼저 받고 나머지는 필요할 때 받습니다.

### 손본 것

페이퍼로지는 space 글리프가 0.22em 으로 좁고 한글 자면이 0.88em 으로 촘촘합니다.
그대로 쓰면 단어가 붙어 보여서 두 가지를 조정했습니다.

- `word-spacing: .04em` 을 본문에 적용
- 제목·작업명의 음수 자간을 절반으로 완화 (앞서 쓰던 가변 글꼴 기준값이었습니다)

### 숫자와 코드

WBS 코드, 날짜, 수치는 **JetBrains Mono** 로 두어 표가 세로로 정렬되게 했습니다.
이 글꼴만 구글 폰트 CDN 에서 받습니다.

**사내망에서 CDN 이 막혀도 정렬은 유지됩니다.** 페이퍼로지 숫자가 전부 0.667em
고정폭이라 대체 글꼴로 들어가도 열이 어긋나지 않습니다 (차단 상태로 확인 완료).

완전히 오프라인으로 쓰려면 두 곳만 지우면 됩니다.

1. `index.html` 의 구글 폰트 `<link>` 와 `preconnect` 줄
2. `app.css` 의 `--mono` 값에서 `'JetBrains Mono',`

## 9. 엑셀로 WBS 고치기

앱에서 엑셀을 내려받아 고친 뒤 다시 올리면 반영됩니다. 151건을 한 번에 정리할 때 씁니다.

### 순서

1. **WBS 트리** 화면에서 `엑셀 내려받기`
2. 노란 칸을 고칩니다 (작업명 · 산출물 · 담당자 · 계획시작 · 계획종료 · 진척률 · 상태)
3. 같은 화면에서 `엑셀 올리기`
4. **무엇이 바뀌는지 미리보기가 먼저 뜹니다.** 확인하고 반영을 누릅니다

내려받은 파일은 **고칠 칸이 노랑, 고정 칸이 회색**으로 칠해져 있습니다.
상태는 드롭다운, 진척률은 0~100 입력 검증이 걸려 있고, 머리글 틀고정과 자동필터도 들어 있습니다.
인쇄하면 가로 A4 폭에 맞춰집니다.

`WBS_수정양식.xlsx` 는 같은 코드로 만든 빈 양식입니다. 앱에서 내려받은 것과 서식이 동일합니다.

> **참고** — 엑셀 쓰기는 자체 구현한 `xlsx-writer.js` 를 씁니다.
> SheetJS 커뮤니티 버전은 셀 채우기·글꼴·테두리를 쓰지 못해 색이 나오지 않습니다.
> 읽기만 SheetJS 에 맡기고, 쓰기는 직접 XML 을 만들어 zip 으로 묶습니다.

### 열 (10개)

| 열 | 고칠 수 있나 | 비고 |
|---|---|---|
| WBS | ❌ | 각 행을 알아보는 열쇠. 절대 바꾸지 마세요 |
| 레벨 · 상위 | ❌ | 새 행을 더할 때만 채웁니다 |
| 작업명 · 담당자 | ✅ | |
| 계획시작 · 계획종료 | **L4만** ✅ | 상위(L1~L3)는 회색·고정. 셀 서식은 아무거나 써도 됩니다 |
| 일수 | ❌ | `NETWORKDAYS` 수식. 주말·공휴일 제외. 날짜를 고치면 엑셀이 다시 계산 |
| 진척률 | ✅ | 0~100. **L4 Task 만** 입력. 상위는 자동 롤업 |
| 상태 | ✅ | 미착수 / 진행중 / 완료 / 지연 |

> 여러 건을 한 번에 정리하기 쉽고, 누가 언제 무엇을 바꿨는지 파일로 남습니다.

> **산출물 열은 뺐습니다.** 데이터는 그대로 남아 트리 검색에서 계속 찾아지지만,
> 엑셀로는 고칠 수 없습니다.

행 순서를 바꾸거나 정렬해도 됩니다. WBS 코드로 찾아가기 때문입니다.

### 표에서 바로 지우기

엑셀을 거치지 않고 트리에서 직접 지울 수 있습니다.

1. 맨 왼쪽 체크박스로 지울 Task 를 고릅니다 (머리글 체크박스는 화면에 보이는 것 전체)
2. 위에 뜨는 빨간 막대에서 `삭제` 를 누릅니다
3. **무엇이 지워지는지 목록이 먼저 뜹니다.** 확인 후 삭제

상위 Task 를 고르면 하위가 함께 지워지고, 선택 막대와 확인 창에 몇 건인지 미리 나옵니다.
검색이나 필터를 걸어 둔 상태에서 고른 선택은 필터를 풀어도 유지됩니다.

**되돌리기는 없습니다.** 지우기 전에 `엑셀 내려받기` 로 현재 상태를 받아 두세요.
확인 창에도 같은 안내가 나옵니다.

Supabase 모드에서 삭제가 거부되면 화면이 원래대로 돌아가고 사유가 표시됩니다.
`42501` 이 나오면 `supabase/fix-write-permission.sql` 을 실행하세요.

### 날짜가 그대로 들어갔는지 앱이 직접 확인합니다

날짜는 이 도구에서 가장 틀어지기 쉬운 값이라, 반영한 뒤 **파일과 한 건씩 대조**합니다.

- 미리보기: `날짜 N건을 파일에 적힌 그대로 넣습니다`
- 반영 후: `반영 완료 — 수정 5 · 추가 0 · 삭제 0 · 날짜 220/220 일치`

**한 건이라도 어긋나면** 토스트 대신 대조 결과 창이 뜹니다.

```
날짜 대조 결과            220건 중 210건 일치 · 10건 불일치
2.1.1.1  계획시작  엑셀 2026-10-12 / 화면 2026-10-10
```

바뀐 날짜만이 아니라 **파일에 적힌 L4 날짜 전부**를 대조합니다.
그래서 값이 조용히 틀어지는 일이 없습니다.

> 검증 장치가 실제로 작동하는지 확인하려고, 일부러 하루 밀리는 버그를 심어 돌려 봤습니다.
> 10건을 정확히 잡아내고 화면에 띄웠습니다.

### Mac Excel (1904 날짜 체계)

Mac Excel 로 저장한 파일은 1904년 기준 일련번호를 씁니다. 1900 기준으로 읽으면
모든 날짜가 4년 1일씩 어긋납니다. 통합문서의 `date1904` 플래그를 읽어 기준일을 맞추고,
그런 파일이면 미리보기 부제에 `1904 날짜 체계 (Mac Excel)` 라고 표시합니다.

### 왜 ID 열이 있나요 (중요)

**WBS 코드는 번호 정리로 바뀝니다.** 코드를 Task 의 신원으로 쓰면 이런 일이 생깁니다.

```
1. 앱에서 2.1.1.2 를 지움 → 번호 자동 정리
     2.1.1.3 "인터뷰 2차"  →  2.1.1.2 로 당겨짐
2. 번호 정리 전에 받아둔 엑셀에서 2.1.1.3 의 날짜를 고쳐 올림
3. 그 날짜가 지금의 2.1.1.3 = "요구사항작성(2차)" 에 들어감  ← 엉뚱한 Task
```

그래서 엑셀 맨 앞에 **ID 열**(`T0001` …)을 둡니다. 코드가 바뀌어도 ID 는 그대로라,
올릴 때 코드가 아니라 ID 로 짝을 찾습니다. **회색 고정 칸이니 지우거나 고치지 마세요.**

- ID 가 있는 파일 → 오직 ID 로만 짝을 찾습니다. 코드로 되짚지 않습니다
- ID 가 없는 옛 파일 → 코드로 찾되, **미리보기에 경고**가 뜹니다
- 파일에 있는 ID 가 앱에 없으면 → 지웠던 Task 로 보고 `되살림` 표시와 함께 안내합니다

Supabase 를 함께 쓰신다면 `supabase/migrate-task-uid.sql` 을 한 번 실행하세요.
실행하지 않아도 앱은 브라우저에서 ID 를 만들어 씁니다.

### 시간대와 날짜 (중요)

엑셀 날짜는 **1899-12-30 기준 일련번호**로 저장됩니다. 이걸 날짜로 되돌릴 때
지역 시차를 쓰면 나라에 따라 하루가 밀립니다.

**한국이 정확히 그 경우입니다.** 1899년 한국 표준시는 UTC+8:27 이었고 지금은 UTC+9:00 입니다.
33분 차이 때문에 변환값이 자정 33분 전으로 떨어져 **전날**로 읽힙니다.

그래서 변환을 라이브러리에 맡기지 않습니다.

- 읽기: `XLSX.read(..., { cellDates:false })` 로 **숫자 그대로** 받습니다
- 변환: `Date.UTC(1899,11,30) + 일련번호 × 86400000` 으로 **UTC 로만** 계산합니다
- 혹시 Date 객체가 들어오면 **가장 가까운 자정으로 반올림**해 하루 밀림을 막습니다

15개 시간대에서 내려받고 그대로 올려 `수정 0` 을 확인했습니다.
서울 · 도쿄 · 상하이 · 콜카타 · 뉴욕 · LA · 상파울루 · 런던 · 베를린 · 시드니 ·
키리티마티(UTC+14) · 미드웨이(UTC-11) · 카트만두(+5:45) · 유클라(+8:45).

### 날짜 셀 서식

**엑셀에서 셀 서식을 바꿔도 됩니다.** 날짜 셀은 표시 형식이 아니라 내부 값을 읽습니다.
아래 여섯 가지로 시험해 모두 통과했습니다.

| 서식 | 화면 표시 | 결과 |
|---|---|---|
| `yyyy-mm-dd` | 2026-09-01 | ✅ |
| `yyyy". "m". "d` (한국 기본) | 2026. 9. 1 | ✅ |
| `yyyy"년" m"월" d"일"` | 2026년 9월 1일 | ✅ |
| `m/d/yyyy` | 9/1/2026 | ✅ |
| `yy-mm-dd` | 26-09-01 | ✅ |
| `General` (일반) | 46266 | ✅ |

셀에 **글자로 직접 적는 경우**는 `2026-09-01`, `2026.09.01`, `2026/09/01`,
`2026년 9월 1일`, `20260901`, `26-09-01` 을 알아봅니다.

`9/1/2026` 처럼 **글자로** 적힌 것은 9월 1일인지 1월 9일인지 알 수 없어
추측하지 않고 문제로 표시합니다. 셀 서식을 날짜로 바꾸면 그대로 통과합니다.

### 엑셀에서 추가와 삭제

- **추가**: 새 행에 WBS · 레벨 · 상위 · 작업명을 채웁니다. 상위가 실제로 있는 코드여야 합니다
- **삭제**: 행을 지우면 *삭제 후보*로 표시만 됩니다. 실제로 지우려면 미리보기에서 따로 켜야 합니다.
  일부만 골라 올렸다가 나머지가 통째로 지워지는 사고를 막기 위한 장치입니다.
  상위 Task 를 지우면 하위 Task 도 함께 지워집니다

### 잘못된 값

반영을 막지 않고, 그 행만 건너뛰고 미리보기에 이유를 적어 줍니다.

```
30행 2.1.6.1  상태 '보류중' 는 쓸 수 없는 값입니다.
31행 2.1.6.2  계획시작 '내일' 를 날짜로 읽을 수 없습니다.
```

Supabase 모드에서 반영 중 오류가 나면 화면 상태를 통째로 되돌립니다. 일부만 적용되는 일은 없습니다.
